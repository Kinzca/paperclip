# 通用任务工作流

共享执行提示词统一规定轻量执行、测试触发条件和禁止交付哈希校验；工作流仅安排阶段与职责，公司／项目上下文仅提供业务规范。选择审查模板不等于明确要求测试。默认快速开发；仅明确选择含审查的模板才增加独立审查。

本轮把执行引擎、用途模板、公司／项目上下文及具体任务分开。引擎继续管理依赖、交接、返修、暂停、恢复、超时和预算，不根据公司名、项目名或模型名猜测领域。

## 界面入口

在侧栏「任务工作流」中选择公司默认规则或具体项目，点击「调整规则」。

- 默认模板为 `rapid-development`（快速开发），仅由负责人执行并直接交付；可逆任务不自动测试或独立审查，仅对不可逆风险或用户明确要求运行相应测试。原有 `standard` 保留标识、节点与上限，可显式选择。应用开发、问题修复、研究分析、文档编写使用不同的执行及审查指令。
- 四个新用途模板要求成功运行回执和已登记 work product；研究、文档不强制运行软件构建。回执或文件存在都不表示内容正确，仍需要独立审查。
- 游戏开发位于「可选专业模板」，保留原有并行代码审查、试玩和人工验收。此前已选择的游戏模板不会自动切换；需要时由用户在当前范围选择通用模板并保存。
- 「执行上下文」保存当前范围的规范、交付约定、知识引用；平台、公司、项目和任务的补充按层追加。清空只删除当前层。不要填凭据。
- 「阶段职责绑定」复用本公司的角色或成员。缺少独立审查者时转交负责人；暂停的 Agent 不会自动激活。切换模板清除旧模板的绑定覆盖，工作流图显示生效职责和失败返回阶段。
- 模板选择不改变人员汇报关系。任务的工作目录、运行工具及登录仍由已有项目工作区和 Agent 适配器提供。

## 任务交接和证据

新通用任务使用交接协议 v1，并在运行快照中保存协议版本、上下文、最终绑定与规则版本。历史快照不追加新要求。

交付复用已有证据，标明实际产物与 Git、run 或 revision ID，并如实说明未验证项。不为普通任务额外创建计划、报告、脚本、抽样或录屏来取证；真实文件交付仍使用原生交付入口。返修保留原验收标准，按需回应问题。概览不再展示“生效的执行上下文”和“规则适用说明”；调整规则中的上下文编辑入口及后台继承保持不变。

新协议的 Agent 审查必须随 decisions 提交 `report`，包含 `artifact`、`revision`、`criteria[]` 和 `findings[]`。验收项包含编号、要求、passed/failed/unverified 和证据；问题包含编号、对应验收项、问题和返修要求。接口拒绝重复编号、未知验收项、未验证却通过、带未解决问题却通过，以及没有可执行问题的退回。

结构化报告存入 attempt.evidence，问题和证据进入返修正文；任务详情以条目展示，原始 JSON 保留在折叠区。历史 attempt 没有报告时不伪造内容。人工决定保留原有说明入口，并在原始证据中标明来源。

**边界：**这些是审查者提交的证据声明。服务端检查结构和结论一致性，尚不自动解析所有原始需求来证明覆盖完整，也不自动确认任意引用的真实性。明确需求缺失时由 Agent 提问／上报阻塞。计划与交付目前是统一文字协议，并非新增独立计划审批节点。服务端按结构化审查问题与产物版本识别重复无进展，并保留尝试次数、时间和费用硬限制；详情见[运行控制说明](WORKFLOW-RUNTIME-CONTROLS.zh-CN.md)。

## 候选改进

「改进此工作流」填写执行指令、改进原因以及四项依据：适用任务与排除情况、问题和来源证据、拟议改进及预期收益、验证办法及回归风险。

依据保存在该公司候选修订的 `definition.improvement` 中；它是候选说明，不是自动扩大执行范围的权限规则。已有不带此字段的草案兼容。保存新结构化建议时四项必须完整。

验收门禁和既有协议不能由优化候选删除。原有至少三个不同任务目标的回归与人工发布机制保留；比较时还检查上下文、限制、执行者和原有审查阶段负责人是否一致，变化会阻止这次比较被计为通过。模型配置与机器环境没有新增冻结，因此不能据此声称严格科学对照。回归重放属于已知任务兼容检查，不等于未见任务评测或普遍质量提升。

本轮不启动回归任务，不自动发布候选，不自动把建议写进 Wiki／全局提示词，也不执行框架自身代码升级。Wiki 和技能来源可写入项目上下文供执行者使用；尚无新增自动检索服务。正式采用仍沿用用户可核查的候选与发布路径。

## 兼容与部署

新增字段存入既有 JSON 列，无新增 SQL 表或迁移。后端、shared 与 UI 必须配套部署；仅推送代码或替换 UI 不代表后端接入。

使用[统一发布流程](LOCAL-RELEASES.zh-CN.md)从确切提交配套构建后端、shared、SDK 与 UI，再备份、迁移和切换版本。保持该电脑实例的数据库、插件路径与登录配置；不提交业务数据。

## 交给用户检查的场景

1. 默认列表展示五种通用用途，游戏模板单独折叠，旧选择可见且不会自动改写。
2. 在公司和项目分别填写上下文、职责，保存后查看继承；切换模板检查绑定是否清理。
3. 新建一个符合准入条件的标准根任务，检查子任务收到的目标、协议和上下文。
4. 用真实证据完成审查、退回、返修和复审，在任务详情核对版本与逐项记录。
5. 保存改进建议，查看候选依据。启动回归会实际调用 Agent，由用户决定何时执行。

开发构建、静态检查或隔离测试不能代替以上业务验收。
